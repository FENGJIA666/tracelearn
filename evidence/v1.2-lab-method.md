# Counterexample Lab: computation and checking method

Version 1.2, 15 September 2026. This note describes the implemented teaching models and their automated checks. It is separate from the frozen 160-request AI experiment and does not report learning outcomes.

## What executes

`src/lab-model.ts` implements two deterministic models. Neither calls an AI service.

The SQL model accepts numbers and NULL, keeps row order and duplicates, and computes TRUE, FALSE or UNKNOWN for four supported predicates:

- `value <> target`
- `NOT (value = target)`
- `value <> target OR value IS NULL`
- `value NOT IN (list)`

WHERE retains only TRUE. The interface supports 1–6 rows, finite numeric values from −1 billion to 1 billion or NULL, and 1–8 NOT IN entries. It does not parse arbitrary SQL. The core function additionally handles an empty list using SQLite's behavior; the interface does not expose empty-list input. See the [SQLite expression documentation](https://www.sqlite.org/lang_expr.html#the_in_and_not_in_operators) for that dialect-specific boundary.

The key model starts with selected attributes and repeatedly applies any stated dependency whose left side is already available. Each trace step records the applicable rule, newly added attributes and resulting closure. A superkey reaches the complete relation. For superkeys, the production model tests each single-attribute removal to check inclusion minimality.

The interface offers two fixed schemas:

| Schema | Stated dependencies | Attribute subsets checked |
| --- | --- | --- |
| R(A, B, C, D) | A → B; B → C | 16 |
| R(S, C, I) | SC → I; I → C | 8 |

These dependencies are given constraints, not inferred from sample data. The computation checks closure and key minimality; it does not claim a general normal-form analyzer.

## SQL differential checking

`tests/lab-model.test.ts` compares the production output with actual parameterized SQLite expressions in a fresh in-memory database. The reference side executes SQL; it does not use the production Boolean functions to derive its expected result.

The main matrix combines five comparison targets, four modes, eight lists and ten input rows: **1,600 row-result comparisons**. Rows include NULL, negative values, signed zero, fractions and duplicates. Lists include empty, NULL-only, numeric, mixed numeric/NULL and duplicate-entry cases. Some list combinations intentionally repeat the same semantics for modes that do not use a list; the count is not 1,600 independent scenarios.

For each row, the test checks both the truth value and WHERE inclusion. Additional tests compare every three-valued NOT, AND, OR and equality entry with SQLite. Separate checks cover default NOT IN behavior, empty row input, malformed numbers, unsupported modes and unchanged caller arrays.

This establishes agreement on the tested fixed SQL subset. It does not establish equivalence for arbitrary SQL, database type coercions, collations or all database products.

## A different algorithm checks the key model

The production code uses iterative attribute closure. The reference implementation in `tests/lab-model.test.ts` instead enumerates pairs of binary tuples for each fixed schema, filters pairs that satisfy every stated FD, and inspects attribute agreement. It does not call `closureTrace()` or `analyzeKey()` to compute the expected closure.

For all **24 attribute subsets** across the two schemas, the checks compare closure, superkey status, inclusion minimality, missing attributes and removable attributes. The oracle evaluates every proper subset when checking minimality, while the production code uses single-attribute removals. Another check replays every returned trace step, requiring the rule's left side to have been reached before any attribute is added.

Additional fixtures exercise reordered rules, cycles, duplicate selections, empty determinants, the empty relation, unknown attributes, immutable schema definitions and source links. These extend edge coverage; they are not an exhaustive proof of all possible dependency systems.

Here, **independent** means a separate computation with a different algorithm. Development and test design were AI-assisted. There was no independent human evaluator or classroom study.

## Record and export integrity

`src/lab-history.ts` stores inputs and predictions, not trusted computed scores. Each record includes an ID, timestamp, schema version and original-course SHA-256. Only the latest 100 valid records for the matching source hash are restored.

Nine targeted history tests check round-trip restoration, foreign source hashes, malformed data, bounded input values, schema/attribute validation, retention limits and both experiment types. Deliberately forged score, truth, closure, source-label and trace fields are discarded. Export recomputes SQL results or key analysis from the stored inputs and fixed model. This protects the report from accepting fabricated derived fields; browser storage remains user-editable and is not tamper-proof assessment evidence.

Lab predictions are stored separately from curated quiz attempts and do not contribute to Notebook correct-answer totals. Exported records describe practice only and explicitly avoid claiming mastery or learning gains.

## Reproduce the checks

From the project root after installing locked dependencies:

```sh
npx tsx --test tests/lab-model.test.ts tests/lab-history.test.ts
npm test
```

The complete v1.2 suite passed **48 automated checks**, including unit and isolated HTTP integration tests. Beyond the Lab, it covers source-practice planning, duplicate completion, installation identity, request-context changes and the earlier course/model-interface checks. A mocked model response is used in the new generator HTTP regression test so it checks the route deterministically; that test is not a new real-model measurement.

Current browser, export, build and release observations belong in `evidence/v1.2-acceptance.md`. Earlier v1.0/v1.1 acceptance records retain their original dates and counts. `server/ai.ts`, the original course and all `evaluation/*` files remain unchanged in this iteration.
